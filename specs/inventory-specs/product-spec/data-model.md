# Product Data Model

## Product

Catalog aggregate representing a sellable inventory item.

Fields:

- `product_id`: integer primary key, generated by the database, immutable.
- `product_name`: required string, maximum 100 characters based on the existing model; canonicalized by trimming, collapsing repeated whitespace, and uppercasing. Must be unique by canonical value.
- `product_name_normalized`: implementation-managed canonical value used for the database uniqueness constraint and indexed lookup if the implementation chooses the dedicated-column design from `research.md`.
- `category_id`: required integer foreign key to `category.category_id`; immutable unless changed through an authorized product update.
- `cost_price`: required `Decimal`, non-negative, `NUMERIC(10,2)`.
- `sale_value`: required `Decimal`, non-negative, `NUMERIC(10,2)`.
- `available_quantity`: required integer, default 0, never negative. Product-level quantity available for future allocation; not a stock-specific quantity.
- `product_status`: required `StatusEnum`, one of `ACTIVE`, `INACTIVE`, or `DISCONTINUED`; defaults to `ACTIVE`.

Relationships:

- Product belongs to exactly one existing Category.
- Product may be referenced by future Stock/StockItem and SaleItem records. Product management must preserve the identifier and must not physically delete the row.

Validation and invariants:

- Name is required, non-blank, normalized before comparison/storage, and unique case-insensitively after normalization.
- Category must exist for creation and category replacement. Creation and reactivation require an ACTIVE category.
- Prices must parse as Decimal, be non-negative, fit the declared precision/scale, and not be silently rounded.
- Quantity is initialized to zero and cannot become negative. Quantity-changing stock workflows are outside this feature.
- Status must be represented by the domain enum/database constraint.
- A failed create/update/status operation persists no partial changes.
- No product deletion operation may remove the row.

## Category (existing aggregate)

Existing entity in `domain/inventory/category.py` and `models/inventory_models/category_model.py`.

- `category_id`: integer identifier.
- `category_name`: canonical uppercase category name.
- `category_status`: existing `StatusEnum` lifecycle value.

Product operations consult Category status but do not change Category.

## Status transitions and capabilities

| Current status | Requested status | Result | Product-side capability |
|---|---|---|---|
| ACTIVE | INACTIVE | allowed | no stock entry; no sale |
| ACTIVE | DISCONTINUED | allowed | no stock entry; sale remains permitted by contract |
| INACTIVE | ACTIVE | allowed only with active category | stock entry and sale permitted by contract |
| DISCONTINUED | ACTIVE | allowed only with active category | stock entry and sale permitted by contract |
| same status | same status | idempotent or accepted without data loss | unchanged |

The implementation must reject any transition the finalized domain policy does not permit and return a domain error. Sale execution and stock movement execution are not implemented here.

## Persistence constraints to add or verify via Alembic

- Non-null constraints for category, name, prices, quantity, and status.
- Foreign key from product category to category.
- Unique constraint/index for canonical product name.
- `cost_price >= 0`, `sale_value >= 0`, and `available_quantity >= 0` checks.
- Status constrained to the three recognized values, using the project's existing PostgreSQL enum strategy or an equivalent CHECK constraint.
- Explicit defaults of zero for quantity and ACTIVE for status.

## Transaction boundaries

Each create, edit, and status change is one transaction. The service validates the full proposed state, the repository applies it, and one commit occurs. On expected validation or integrity failure, the transaction is rolled back and the API receives a stable error without a partially updated Product.
